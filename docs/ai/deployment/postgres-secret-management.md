# Postgres password & secret management

## When to read this
- Deploying, copying, or editing any production stack's Postgres / pgbouncer credentials.
- Rotating the Postgres password for a dictionary or aggregation stack.
- Debugging `FATAL: password authentication failed for user "postgres"` from pgbouncer, or a Postgres role created with no/`trust` password.
- Questions about why `AUTH_TYPE: plain`, why there are **two** secrets per stack, or why `entrypoint:` wrappers aren't used.
- Deploying through **Swarmpit** (its compose parser has the quirks this design works around).

## Concepts

Every production indexer stack runs `app/processors → pgbouncer → Postgres`. The Postgres credential is **not** stored in YAML/git. It lives as **two paired Docker Swarm secrets** per indexer, both `external: true`, created once on the swarm and reused by every stack of that indexer.

### The two secrets (per indexer)

The pattern is identical for both indexers; only the secret **names** differ:

| Indexer | Raw-password secret | pgbouncer-userlist secret |
|---|---|---|
| storage-dictionary (all `st-dict-*` stacks) | `STORAGE_DICTIONARY_PG_PASSWORD` | `STORAGE_DICTIONARY_PGBOUNCER_USERLIST` |
| aggregation (`orca-full-orca.yml` / `orca-full-catfish.yml`) | `AGGREGATION_INDEXER_PG_PASSWORD` | `AGGREGATION_INDEXER_PGBOUNCER_USERLIST` |

Contents:

| Secret | Exact bytes | Consumed by |
|---|---|---|
| `*_PG_PASSWORD` | the raw password string, **no trailing newline** | • Postgres service via `POSTGRES_PASSWORD_FILE: /run/secrets/<name>`<br>• API service command: `export DB_PASS=$(cat /run/secrets/<name>) && sqd api:prod`<br>• processor anchor command: same export before `sqd migration:apply && node lib/main.js` |
| `*_PGBOUNCER_USERLIST` | a literal pgbouncer userlist line: `"postgres" "<raw password>"` | pgbouncer service — mounted directly at `/etc/pgbouncer/userlist.txt` (`target:`, `mode: 0444`) |

Both secrets must carry the **same** raw password; the userlist one just wraps it in pgbouncer's `"user" "pass"` syntax. They are tied together by convention, not by Docker — keep them byte-identical in the password portion.

### Why two secrets and not one
Two consumers need the password in **different formats**: Postgres wants the raw string; pgbouncer wants a `"user" "pass"` userlist line. Swarm secrets are immutable and **not templated**, so there's no way to derive the userlist from the password at deploy time. Pre-baking the userlist as its own secret is the clean way to give pgbouncer the exact bytes it needs.

### Why pgbouncer runs `AUTH_TYPE: plain` (this is correct, not a TODO)
- `auth_type` governs how **clients (api/processor) authenticate to pgbouncer**, not how pgbouncer authenticates to Postgres.
- With a **plaintext** password in the userlist, pgbouncer holds the plaintext and can derive a fresh **SCRAM proof** for each backend connection to Postgres → backend auth succeeds.
- If the userlist instead held a SCRAM verifier or md5 hash, pgbouncer would have no plaintext and **cannot** complete SCRAM against Postgres (SCRAM is challenge/response — it needs the plaintext to compute a proof for Postgres's own salt). That failure shows up as pgbouncer accepting clients then logging `FATAL: password authentication failed for user "postgres"` on every backend login.
- The client→pgbouncer hop sends plaintext, but it is entirely on the stack-internal `<stack>_default` overlay network — no trust boundary crossed. Full client↔pgbouncer SCRAM would require `auth_query` against Postgres (significantly more setup; not done here).

### Why the userlist is mounted as a secret (not generated by the image)
The `edoburu/pgbouncer` entrypoint *can* generate `/etc/pgbouncer/userlist.txt` from `DB_USER`+`DB_PASSWORD`, but it is unreliable: it only writes the file if one doesn't already exist (silently no-ops against the baked-in default), and it couples the file format to `AUTH_TYPE` (writing a SCRAM verifier under `scram-sha-256`, which then can't auth to Postgres — see above). Mounting our pre-baked userlist read-only at `/etc/pgbouncer/userlist.txt` bypasses that logic entirely: the file already exists, so the entrypoint leaves it alone, and `mode: 0444` means it couldn't overwrite it anyway. **Therefore the pgbouncer service must NOT set `DB_PASSWORD` / `DB_PASSWORD_FILE`** — that would invite the entrypoint to regenerate the userlist.

### Why no `entrypoint:` wrappers (Swarmpit constraint)
The natural fix — override `entrypoint:` with a shell wrapper that exports the secret then `exec`s the image's real entrypoint — **does not survive Swarmpit**. Swarmpit's compose parser silently **strips `entrypoint:`**; only `command:` propagates. A stripped wrapper means `POSTGRES_PASSWORD` is never set and Postgres `initdb` creates the `postgres` role with no password (`enabling "trust" authentication`). So this design uses only mechanisms Swarmpit propagates reliably:
- **env vars** (including `*_FILE` ones — the `postgres:15` entrypoint reads `POSTGRES_PASSWORD_FILE` natively),
- **secret mounts with explicit `target:` paths**, and
- **`command:` shell wrappers** that `export DB_PASS=$$(cat /run/secrets/...)` before launching the app (this works because we wrap the *app* command, not the image's entrypoint).

### Creating the secrets on the swarm
Use `printf` (no trailing newline) — never `echo` (adds `\n`, which silently corrupts the auth chain because some entrypoints strip it and others don't). Example for the dictionary:
```sh
printf '%s' '<raw password>'                | docker secret create STORAGE_DICTIONARY_PG_PASSWORD -
printf '%s' '"postgres" "<raw password>"'   | docker secret create STORAGE_DICTIONARY_PGBOUNCER_USERLIST -
```
(For the aggregation indexer, substitute the `AGGREGATION_INDEXER_*` names.)

### YAML shape (applies to every stack)
```yaml
secrets:
  STORAGE_DICTIONARY_PG_PASSWORD:        { external: true }
  STORAGE_DICTIONARY_PGBOUNCER_USERLIST: { external: true }

# Postgres
db-dict-...:
  environment:
    POSTGRES_PASSWORD_FILE: /run/secrets/STORAGE_DICTIONARY_PG_PASSWORD
  secrets: [STORAGE_DICTIONARY_PG_PASSWORD]

# pgbouncer  (NO DB_PASSWORD / DB_PASSWORD_FILE here)
dict-db-pgbouncer-...:
  secrets:
    - source: STORAGE_DICTIONARY_PGBOUNCER_USERLIST
      target: /etc/pgbouncer/userlist.txt
      mode: 0444
  environment:
    AUTH_TYPE: plain   # must be plain — userlist is pre-baked with plaintext

# api / processor  (password injected at runtime via the command)
  secrets: [STORAGE_DICTIONARY_PG_PASSWORD]
  command: [sh, -c, "export DB_PASS=$$(cat /run/secrets/STORAGE_DICTIONARY_PG_PASSWORD) && sqd api:prod"]
```
The shared `<<: *…-db-pgbouncer-creds` anchor provides `DB_HOST/PORT/USER/NAME` but **not** the password — the password reaches each app process only via the `export` in `command:`. `$$` escapes Compose interpolation so a literal `$` survives to the shell.

## Rotation playbook
Swarm secrets are immutable → rotation = create new + update YAML + ALTER + redeploy + delete old.
1. Generate the new password.
2. Create both new secrets with versioned names (`*_PG_PASSWORD_V2`, `*_PGBOUNCER_USERLIST_V2`) via `printf | docker secret create`.
3. Update every affected stack's YAML to the `_V2` names (top-level `secrets:` + per-service `secrets:` + the `cat /run/secrets/...` paths in `command:`).
4. **`ALTER USER postgres WITH PASSWORD '<new password>';`** inside each Postgres container — `POSTGRES_PASSWORD_FILE` is only read at `initdb` (first start on an empty volume), so a populated volume keeps the old password until you ALTER it.
5. Redeploy every stack (`docker stack deploy` / Swarmpit).
6. Delete the old secrets once nothing references them (`docker secret rm ...`).

A small script that creates both secrets atomically from one input value is recommended to prevent drift.

## Gotchas
- **`POSTGRES_PASSWORD_FILE` is initdb-only.** On a redeploy against an existing populated volume it is ignored. To change the password on a live deployment you must `ALTER USER`, not just redeploy — otherwise pgbouncer's new userlist won't match Postgres's stored password and all backend logins fail.
- **The two secrets must stay byte-identical in the password portion.** They're coupled by convention only. Drift between them = pgbouncer can't auth to Postgres.
- **Never `echo` a secret in; use `printf '%s'`.** A trailing newline silently breaks the auth chain.
- **pgbouncer must not set `DB_PASSWORD`/`DB_PASSWORD_FILE`.** Setting it invites the entrypoint to regenerate the userlist and clobber the intended plaintext format.
- **`AUTH_TYPE: plain` is intentional, not a leftover.** The `../deployment/docker-swarm-overview.md` note that it "should be scram-sha-256" predates this understanding — plain is required given the pre-baked plaintext userlist + SCRAM backend. Do not switch it without implementing `auth_query`.
- **No `entrypoint:` overrides via Swarmpit.** They get stripped. Keep credential injection in env vars, `target:`-mounted secrets, and `command:` wrappers only.
- **`edoburu/pgbouncer:latest` is a moving target** — entrypoint behaviour has varied across the same tag. Pin the tag for new setups; the userlist-as-secret approach makes you immune to the entrypoint quirk regardless.
- **Plaintext lingering in git.** An external session noted at least one stack (`st-dict-xyk-hist-data.stack.yml`) still carries the old plaintext password in a *commented-out* migration-job block. Commented blocks don't deploy, but the literal value is in history — scrub before sharing the repo publicly. Verify against the current file before acting.
- **`<<: [anchor1, anchor2]` array-merge** in processor `environment:` blocks is accepted by docker-compose but flagged by strict YAML 1.1 linters ("Single value is expected"). If you adopt a stricter validator, flatten to a single anchor.
- **Path/name note (verify before relying):** an external session described a parallel set of secret-enabled stack files under `storage-dictionary/selfhosted/stacks-with-secret/` (e.g. `st-dict-lbp-hist-data-v21.stack.yml`, deployed as `stdict-lbp-v2-2-self`, etc.). The active stacks in *this* repo live at `self-hosted/storage-dictionary-indexer/st-dict-*.stack.yml` and already follow this pattern. If you can't find a referenced file, it may belong to that external layout or to swarm deployment metadata, not this repo tree.
